# 多 Agent 研究、长期记忆与恢复指南

当前研究模式是一套**有预算、能复用、可恢复的小型研究流程**。以下描述实际实现，默认参数和版本号由[代码事实参考](reference.md)维护，运行命令集中在[运行指南](operations.md)。

## 1. 运行

```bat
conda activate agent
agentic-rag "分析一下2027年猪肉价格走势"
```

在另一台机器或重新安装环境时：

```bat
python -m pip install -e ".[dev]"
```

研究模式默认打开；知识目录的自动监听仍默认关闭。不要把项目说明放进 `knowledge/`，本文件仅供开发者阅读。

## 2. 实际工作顺序

1. CLI 给本次研究创建编号，LangGraph 保存节点检查点。
2. 路由器生成任务类型、数据源、查询词、时间建议和待核对因素；终端展示实际采用的参数。
3. 选择新闻源且时间计划有效时，长期记忆用关键词索引和向量索引联合召回已读文章；随后仍检查在线来源，避免只依赖旧记忆。记忆召回先于在线收集。
4. 本地知识、新闻 API、公开搜索并行收集，去重后保留来源。新闻候选按预算选出，再获取正文；不会向量化整个远端新闻库。
5. 阅读 Agent 按段阅读入选新闻。程序先标记句子编号，模型选择支持事实的句子，程序回填精确原文及位置。不同文章/片段可以同时处理。
6. 筛选器判相关性；证据评估器检查是否足以回答。已有处理结果不会因为补搜而全部清空。
7. 调度器根据核对因素，最多取 `SPECIALIST_COUNT` 个目标创建专题 Agent（默认三个）；事实型问题或无入选证据时跳过。每个任务有独立目标、输入与结果，可请求一轮 `read_news`，最多回读两篇当前证据中的已保存新闻片段，不是无限制精读全文。
8. 缺失关键事实时追加补搜；已经足以条件分析、查询重复、连续无新增、达到轮次或任务预算时停止扩张。
9. 生成器综合当前证据和专题建议，给条件判断；评审同时检查依据和任务完成度。不通过时有界重写/补搜，预算耗尽仍不通过则明确失败，不伪装成已核验答案。

预测可以从当前事实推导，不要求新闻里已经写好未来答案。专题自动补搜会过滤“未来年份 + 预测”这类追逐确定未来数值的请求，并在终端说明；它不会擅自更改用户明确的日期条件。这是启发式护栏，不是完整语义判定器。

## 3. 增强向量数据库怎样存

这里的“增强”是**原文与版本 + 结构化阅读成果 + 混合召回 + 可修复索引**，不是把所有内容塞进一个向量。

| 存储 | 保存什么 | 用途 |
|---|---|---|
| SQLite `research.sqlite3` | 原文版本、片段、引用位置、阅读覆盖率、任务、事件、缓存 | 可靠记录与精确去重的事实源 |
| SQLite FTS5 | 中文双字词与英文关键词倒排索引 | 关键词命中，BM25 排序 |
| Chroma `news_chunks_*` | 原文片段向量及文章/版本/片段编号 | 可重建的原文语义索引；当前回读用原文库定位 |
| Chroma `reading_memory_*` | 阅读事实、观点、原文引用的向量 | 当前长期记忆的主要语义召回入口 |
| Chroma `task_analysis_*` | 专题结论向量、问题、证据哈希、模型版本、运行编号 | 持久化分析投影；当前专题复用走严格任务键，不把相似结论直接当事实 |
| SQLite `checkpoints.sqlite3` | LangGraph 节点状态 | 从未完成节点继续 |
| 原有新闻向量缓存 | 候选标题/摘要向量 | 从本次 API 候选中排序，独立于阅读成果 |
| 原有最终答案缓存 | 已核验答案及证据身份 | 同问题、同实际证据等条件下复用，原有 TTL 仍生效 |

关键词与向量各取有限候选，SQLite 检查当前文章版本与阅读版本，程序校验日期，再用 RRF 合并有效候选排名。先召回再读取，不为每次问答加载整个文章库。旧版本留档，但不会作为该文章的当前版本自动召回。

向量写入与模型阅读解耦：阅读成果和“待同步向量”在同一 SQLite 事务落盘；即使 Chroma 暂时失败，也不必重新调用模型。修复命令只重建投影。

## 4. 怎样认定“已经分析过”

不能靠标题相同或语义相似来判断。

- **文章身份**：数据源 + API 文章 ID（缺失时使用 URL/来源标识）。同标题、不同 ID 不自动合并。
- **内容版本**：规范化正文 + 标题、发布时间、材料类型、来源，计算 SHA-256。只清理格式，不删除数字和单位。
- **阅读版本**：阅读规则版本 + Ollama 实际模型摘要及相关生成设置 + 分段长度。
- **片段任务键**：文章身份 + 头信息 + 当前片段正文哈希 + 阅读版本。
- **专题任务键**：目标 + 原始问题 + 实际证据上下文 + 原文版本 + 模型版本 + 规则版本 + 当天日期。

全部片段都完成，才记作 `complete`；部分完成是 `partial`。完整表示“所有片段已按流程处理”，**不代表模型提取了原文所有信息，也不代表报道事实已经独立核实**。

正文变动会产生新版本；分段边界未变且内容相同的片段仍可复用。插入内容导致后续分段边界变化时，可能重读多个片段，这是当前按字符分段方案的边界。

更换阅读提示词/模型，需要新阅读成果；更换嵌入模型，只需重建向量，不需要重新阅读。嵌入命名空间按配置名称区分：如果本地同一路径的嵌入权重原地替换，请换一个版本化路径/名称，系统不会自动识别权重文件变化。

## 5. 并发是真实的，但有上限

默认值在 `.env.example`；已有 `.env` 未填写时自动使用默认值。

| 配置 | 默认值 | 含义 |
|---|---:|---|
| `AGENT_WORKERS` | 4 | 每批最多同时工作的子任务 |
| `LLM_CONCURRENCY` | 2 | 进程内最多两个模型请求在途 |
| `IO_CONCURRENCY` | 4 | 进程内受控网络调用上限 |
| `SPECIALIST_COUNT` | 3 | 每轮专题目标数上限 |
| `RESEARCH_MAX_TASKS` | 20 | 同一研究持久化的不同子任务数上限 |
| `RESEARCH_MAX_ROUNDS` | 3 | 补搜轮数上限；不包含初次抓取 |
| `TASK_MAX_ATTEMPTS` | 2 | 子任务失败尝试上限；底层模型请求重试另有配置 |
| `LLM_REQUEST_TIMEOUT` | 120 | 单次模型 HTTP 请求超时秒数 |
| `RESEARCH_TIMEOUT` | 900 | 一批子任务的调度时间预算，不是端到端超时 |
| `READING_CHUNK_CHARS` | 2200 | 一次独立阅读的片段字符数 |
| `MEMORY_RECALL_K` | 3 | 长期记忆补充召回篇数 |

“一个 Agent”在这里是一个有目标、输入、模型调用和持久结果的逻辑任务，不是为每条新闻无限新建操作系统线程。LangGraph 负责阶段编排，Python 线程池负责子任务并行，SQLite 负责去重领取与恢复。

模型槽位与工作线程分离：四个任务中可以有两个在请求模型，其余等待或做其他工作。终端显示的是应用的在途请求数，**不保证 Ollama/GPU 内部真的同时推理两个请求**。如果显存不足或吞吐下降，将 `LLM_CONCURRENCY=1`；并行检索和任务调度仍保留。

并发上限是单进程的；两个 CLI 进程不会共享同一模型信号量。但它们会通过同一 SQLite 原子任务键避免重复计算相同子任务。同一个研究编号不能同时恢复。

## 6. 中断、重试与检查成果

每次启动会显示真实研究编号，下面的 `RUN_ID` / `READING_ID` 要替换成终端里的值。

```bat
agentic-rag --runs
agentic-rag --status RUN_ID
agentic-rag --resume RUN_ID
agentic-rag --resume RUN_ID --retry-failed
agentic-rag --inspect-reading READING_ID
agentic-rag --repair-memory
```

- `--runs` / `--status` / `--inspect-reading` 不调用对话模型。
- `--resume` 使用原检查点；已经完成的研究展示保存的答案。它不是刷新新闻的命令，要新资料请发起新问题。
- `--retry-failed` 重置失败任务的尝试预算，从保存的收集材料重新进入阅读阶段；已完成任务继续复用。
- `--repair-memory` 补齐所有待写向量；遇到错误停止，阅读记录不丢失。它可能加载嵌入模型，但不调用对话模型。
- 修改模型、阅读规则或工作流版本后，不继续混用未完成的旧检查点；发起新研究。已完成旧研究仍能展示。

Ctrl+C 是协作取消：停止追加任务，撤销当前执行者提交权限；已经发出去的 HTTP 请求可能到超时才退出。**不能安全地强杀任意 Python 线程**。异常进程退出后，运行锁约45秒、任务租约默认180秒会到期；不要通过删除数据库来“解锁”。

保存的事件是可核对的任务状态、目标、来源、查询、引用、错误和结论摘要，不是模型隐藏的逐字思维链。

## 7. 学习代码的顺序

1. `cli.py`：从接收问题、分配运行编号到输出事件。
2. `graph/build.py`：主图如何接入召回、阅读和专题调度。
3. `research/service.py`：怎样把问题拆成任务、生成任务键、复用成果和回读原文。
4. `research/scheduler.py`：任务排队、依赖、原子领取、租约、重试与取消。
5. `research/store.py`：文章身份/版本、引用位置、事务与索引待办。
6. `research/memory.py`：Chroma 投影、FTS5 + 向量的混合召回。
7. `research/chains.py`：阅读及专题 Agent 的结构化输出规则。
8. `research/runtime.py` / `research/session.py`：资源槽位与运行互斥。

工具层改造后，还可读[工具层的边界与实际调用](tools-guide.md)。知识、新闻、公开搜索与已保存新闻回读已接入四个真实 `@tool`；`research/service.py` 保留调度与成果管理，不再直接实现原文片段选择。`agentic-rag --list-tools` 可在不调用模型、不初始化研究数据库时查看工具契约。

### 流程图对应关系

[当前研究流程 SVG](agentic-rag-research-flow.svg)是纵向8步总览，评估与专题分析合并展示，详细边见 `graph/build.py`：

1. CLI 接收问题或恢复研究 → 问题与研究编号。
2. 路由器规划数据源与查询条件 → 来源、查询词与日期。
3. 检索器并行取资料 → 去重后的材料。
4. 阅读 Agent 处理分段并保存 → 可追溯的阅读成果。
5. 研究 Agent 核对缺口并专题分析 → 证据可用则生成；缺事实且有预算则补搜。
6. 生成器综合证据 → 候选答案与引用。
7. 评审器核对依据与任务 → 通过则交付；预算内补搜/重写；预算耗尽则交付限制说明。
8. CLI 展示结果 → 用户收到核验结果或未完成说明。

已知边界：

统一问题清单见[当前状态](status.md)，包含尚未修复的数字/单位校验、错误分类、专题长度约束和记忆审核问题；不能因已有原文引用而声称完整事实核验。

- 新闻阅读仅处理本次入选及记忆召回文章；不会预先分析远端所有新闻。
- 网页来源仍是公开搜索摘要，未加入通用网页全文爬虫。摘要不能冒充完整研报。
- 当前混合召回在有限候选后做日期过滤，严格日期范围可能召回较少；不是全库高召回率保证。
- 模型评审可能漏掉价格口径混淆、因果推导错误；通过自动核验不等于预测正确。需要更完善的领域标注评估集与人工复核。
- 文章版本、检查点、事件会增长；当前没有自动清理，避免开发期丢记录。规模上升后需要归档与容量治理。
- 当前是本地单用户演示架构，不是分布式生产调度平台；不保证外部模型调用严格只发生一次。进程崩溃在“模型已返回、尚未保存”的缝隙中，允许重试计算，但拒绝过期执行者覆盖结果。
- 数据位于 `.chroma/`，包含新闻原文、问题和分析成果，请按私有数据保护；不要提交到 Git。
