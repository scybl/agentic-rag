# 运行与维护

以下 Windows 命令示例用 **CMD / Anaconda Prompt**。PowerShell 执行带引号的程序路径才需要前缀 `&`；不要把它复制到 CMD。参数清单见[代码参考](reference.md)。

## 1. 用现有 Conda 环境

在项目根目录执行：

```bat
conda activate agent
python -c "import sys; print(sys.executable)"
python -m pip install -e ".[dev]"
```

确认解释器是你要用的 `agent` 环境。`-e` 是可编辑安装，修改项目源码后重启 CLI 即可加载；新增依赖或更改命令入口后需重新安装。

当前新闻候选排序新增 `scikit-learn`，已有环境也需执行上面的安装命令。此更新不要求清空数据库或重建知识索引；旧未完成研究若版本不兼容，应重新提问。

不用 Conda 时可创建虚拟环境：

```bat
python -m venv .venv
.venv\Scripts\activate
python -m pip install -e ".[dev]"
```

仓库要求 Python 3.10+；依赖下限是声明，不表示每种旧版依赖组合都已验证。没有锁定全部依赖版本。

## 2. 准备模型和配置

仅首次且没有 `.env` 时复制模板：

```bat
if not exist .env copy .env.example .env
ollama pull qwen2.5:3b
ollama list
```

这是仓库示例模型，不强制替换已有模型。`LLM_MODEL` 必须匹配本机模型名称；Ollama 服务须可连接。嵌入模型首次使用可能需要下载，离线时应配置已有本地模型目录。

不要覆盖现有 `.env`。新增设置未填写时使用代码默认值；修改设置后重启进程。私有新闻需要自己的 `NEWS_API_KEY`，不配置时可使用知识和公开搜索，新闻源失败会被记录，并不保证路由自动避开它。

## 3. 放资料并初建

把供模型查阅的 `.md`、`.txt`、`.pdf` 放进 `knowledge/`：

```bat
python -m agentic_rag.ingestion
```

等价命令 `agentic-rag-ingest`。完成后退出，不会持续监听。`docs/` 里的项目说明不是默认检索材料。

## 4. 提问与查看工具

```bat
agentic-rag --list-tools
agentic-rag "什么是事件研究法？"
agentic-rag
```

交互模式在 `>` 后输入问题，`exit` / `quit` 或 Ctrl+C 退出；空输入也退出。入口不在 PATH 时用 `python -m agentic_rag.cli`。`pyproject.toml` 把命令映射到 `agentic_rag.cli:main`，不是运行一个配置文件。

等待新输入默认 300 秒后退出，`--idle-timeout 60` 改为 60 秒，`--idle-timeout 0` 关闭；这不限制研究执行时长。问答退出路径会尝试向 Ollama 发送 `keep_alive=0` 卸载请求（包括单次提问、恢复和交互结束），失败会提示，不强杀服务。同一服务被其他程序共享时，退出也可能影响它们复用已加载模型；诊断/列工具等提前返回的命令不触发卸载。

交互模式自动建立持久化会话，先消解追问再新建独立研究；单次命令默认独立，显式 `--conversation ID` 才承接历史。`/new` 切换新会话，`/history` 查看最近20轮，`/turn N` 回读该轮完整原文。`--no-conversation` 关闭会话功能，`--resume` 仍只恢复同一研究，不能同时指定会话。模型不确定、编号不唯一、引用核对失败时先澄清，不进入研究图。完整示例与预算边界见[会话指南](conversation-guide.md)。

默认终端显示步骤数字、实际查询、人物/机构/主题、精确时间、栏目、指定信息源、排序/覆盖、候选过滤数量、任务进度与异常，保留最终答案和来源；`-v` 展开完整规划、证据判断、核验说明和逐调用用量。模型负责生成查询指令，程序负责类型校验和严格执行，不能自行放宽显式条件。两种模式使用相同账本，也不输出隐藏逐字思维链。

每个人物/机构必须进入至少一组实际查询；主题只是检索线索，不要求模型生成的标签逐字出现在原查询中。编译器最多执行四组查询，在余量内补充主题，并显示“补充主题查询”和“本轮未覆盖主题”。未覆盖不等于已经查过；不会因此暗加日期限制或增加正文预算。明确时间戳保留时区，并按上海自然日粗筛，不能降成全天条件。

### Token 统计怎么看

会话消解的模型调用单独展示并记录在会话轮次的 `resolution.usage`；程序累计包含这部分用量，单个研究的累计不含前置消解。首次完整问题不调用消解模型，确定性的抽取压缩也不消耗模型 Token。字节预算与服务返回的真实 Token 计数严格分开。

重新启动 `agentic-rag` 即默认启用统计，不需重建知识库。默认节点结束显示一行耗时/调用数/用量，逐调用详细输出使用 `-v`；最终回答和来源之后合并显示「Token 最终合计 / 耗时统计」，不重复打印多份总表。区分本次执行、研究历史累计和程序累计（含预热和此前问题，不重复累计恢复前历史）。失败和 Ctrl+C 也输出已知用量及停止诊断。

| 终端字段 | 含义 |
|---|---|
| 输入 | Ollama 报告的 `prompt_eval_count`；不只是你键入的问题，还包括规则、上下文、工具说明、证据、历史反馈等实际请求内容 |
| 生成总量 | Ollama 报告的 `eval_count`；包括内部路由 JSON、阅读结果、筛选结论、专题分析、评审和最终答案，不只是屏幕上的最终回答 |
| 思考 / 可见输出 | 服务明确提供思考 token 细分时再拆开；否则标为未拆分。`think=false` 是请求设置，不是服务已报告思考为 0 的证据 |
| 输入中缓存读取 | 服务提供且 SDK 透传该字段时显示；是输入的子集，不再次相加，也不等同于“应用命中阅读/答案缓存” |
| 输入组成（字符，非 token） | 按 system / human / ai / tool 消息统计字符；帮助理解请求构成，不用字符数估算 token，不显示提示或思考正文 |
| 步骤 / 任务 / 尝试 / 调用编号 | 定位哪个步骤、哪个阅读或专题任务、哪次实际请求产生用量；补搜后重复节点分别列出 |
| 未报告 / 已知小计 | 服务错误、中断或旧版本缺少计数时，不能宣称完整总量，未报告不当作零 |

完整总量 = 所有实际请求的输入 + 生成；思考是生成的子项，缓存输入是输入的子项，都不能重复加总。[Ollama 用量文档](https://docs.ollama.com/api/usage)与[聊天接口字段](https://docs.ollama.com/api/chat)是字段来源。对本地 Ollama，输入是发给本机模型服务，不代表上传云端或 API 费用；若自行配置远程地址则发往该服务。

下面为 `-v` 详细模式格式示例，**不是某次真实研究结果**：

```text
[步骤 Token · 筛选相关证据] 调用 3 次；输入 6,000 + 生成 120 = 已知合计 6,120
[步骤 Token · 分段阅读/复用] 调用 0 次；输入 0 + 生成 0 = 已知合计 0；未调用对话模型
...
最终回答
...
本次问题 Token 统计
  本次执行新增：输入 10,000 + 生成 1,000 = 总计 11,000 token；调用 8 次
  思考/可见输出未完整拆分：8 次；生成总量已计入，不另外相加。
------------------ Token 最终合计 ------------------
  本次执行全部步骤：输入 10,000 + 生成 1,000 = 总计 11,000 token；调用 8 次
  本次程序累计（含预热和本轮之前的问题，不重复计入历史）：输入 10,000 + 生成 1,000 = 已知小计（不是完整总量） 11,000 token；调用 9 次
    用量不完整 1 次（此示例的空提示预热未报告计数）。
```

计量边界与容易误读的地方：

- 阅读/专题成果直接复用没有新增模型调用；但检索、相关性检查、评审仍可能消耗。答案缓存命中后也仍可能核验，不能说整次问题零消耗。
- 模型重试、任务重试、回读后第二次分析、重写均计入。模型返回后即使解析或校验失败，已报告用量仍保留；没有返回计数的失败只能标未知。
- 每条新调用记录实际阶段/本次尝试的思考开关和模型名称，不用全局开关代替；短结构化阶段关闭思考、自适应重试切换思考都能核对。旧记录不会回填成已实测的数据。
- 模型预热用独立表展示，不归入每个问题，但纳入程序累计。空提示加载可能不返回计数，程序累计因此是已知小计；不影响本题自身完整性。
- 研究用量随 `RUN_ID` 存在研究数据库事件中，`agentic-rag --status RUN_ID` 默认显示数字摘要；加 `-v` 输出 JSON，其中 `token_usage.cumulative` 为全量累计，不受最近 100 条事件限制。`current` 是本次查看会话，通常为 0。`complete=false` 时主项只是已知小计，缺失细分是 `null`。
- `--resume` 分开显示“本次新增”和“历史累计”；查看已结束且有保存答案的研究新增调用为 0，也不进行预热、卸载或索引监听。升级前的旧研究没有 token 记录，无法追溯补算。
- 中断时仍在退出的请求标“未返回”；进程还活着且稍后收到计数会继续落盘，可再次查看 `--status`。进程被强杀或服务从未返回的用量无法恢复；落盘失败会明确警告。
- 当前统计 CLI 流程的对话模型请求；嵌入模型、搜索和 SQLite/Chroma 操作不纳入此计量，不代表没有计算开销。独立 RAGAS 评估脚本也不在此 CLI 汇总中。统计不是强制 token 预算或金额账单。

### 计时怎么看

重新启动即可启用，不用改 `.env` 或重建索引。正常完成、异常和 Ctrl+C 都输出已知耗时；计时事件与 token 事件一起保存，不会重新分析旧研究。

| 字段 | 计时范围 |
|---|---|
| 步骤耗时 | 节点开始到结束，包括检索、本地处理、排队、重试和该步骤内的并发任务；未调用模型的步骤也计时 |
| 模型请求耗时 | 每次请求开始到返回/失败的耗时；含网络及服务内部等待，不含调用前的本地模型槽位排队，不是纯 GPU 计算时间 |
| 阅读/专题任务耗时 | 使用调度器已有计时，完成时展示，含线程开始执行后的领取/槽位等待和重试，不含线程池领取任务前的排队；复用不冒充重新执行 |
| 本次执行总耗时 | 进入研究执行上下文到退出，覆盖整张图运行及状态落盘，不含启动预热、等待用户输入、进入执行上下文前的数据库/恢复检查和最终答案打印 |
| 本研究累计执行耗时 | 把各次执行已记录的时间相加，不包含中断后等用户恢复的间隔；已完成研究的离线展示不再新增研究执行事件或耗时 |
| 本程序累计执行耗时 | 本进程新执行的问题及预热之和，不重复累计恢复前历史，也不包含两次输入之间的空闲 |
| 模型请求耗时之和 | 多个请求可能重叠，不能当作研究实际等待时间，也不能再加到总耗时上 |

计时使用单调时钟，系统时间调整不会影响时长。步骤、任务和工具结果耗时默认可见，成功模型请求的逐次耗时在 `-v` 下展开；总时长不会通过相加线程时间计算。`agentic-rag --status RUN_ID -v` 的 `token_usage.timing.cumulative` 查看累计执行时长，`token_usage.timing.steps` 查看所有已记录步骤。`elapsed_seconds` 是秒；`complete=false` 表示只有已知小计。

升级前没有执行开始/结束计时的记录不会补写成零，也不会用模型请求时长之和冒充总耗时；未完成或被强杀的执行也不补造结束时间。后台请求在中断后才返回时，模型耗时可能继续落盘，而该次主流程计时截止于退出。

### 开启本地模型思考

仅支持思考的模型才能设置 `LLM_REASONING=true`。仓库示例默认关闭，首轮输出上限2048、上下文8192、超时120秒；配置事实见代码参考。历史 `gemma4:26b` 实测曾采用8192/16384/300及1100字符阅读片段，不是其他机器的通用最优值，也不是本机此刻有效配置的保证。预热不启用思考；研究各阶段按下文资源策略执行。

输出额度包含思考与可见结果，开启后延迟和生成量可能增加。启动 CLI 会显示实际设置；无需重建知识库。模型指纹包含思考开关，避免混用旧缓存；旧研究不删除，使用新规则要重新提问，不是恢复旧已完成回答。

所有研究链先检查服务停止原因，`done_reason=length` 时拒绝半截 JSON/答案；已消耗 token 仍计入。截断、超时、空输出、结构错误和可恢复服务故障会进入 `plan_model_retry`：程序依据实际用量和硬上限选择临时增加输出/上下文、延长单次超时、关闭思考、反馈格式原因、切分阅读输入或停止。客户端错误和未知错误不盲目重试，半截长输出不回塞下一请求。

自适应默认最多三次模型尝试，实际取 `LLM_MAX_ATTEMPTS` 与 `LLM_ADAPTIVE_MAX_ATTEMPTS` 较小值。动态输出、上下文和超时由对应 `LLM_ADAPTIVE_*` 配置控制；低于首轮值不会追溯压低首轮，设置过高会增加内存与等待。`RESEARCH_TIMEOUT` 仍是一批任务的调度预算，不是整场上限。

首轮不再给每个节点一律分配全局最大输出。路由、文档相关性、阅读和答案评审分别使用与结构契约匹配的较小预算，并默认关闭深度思考；证据综合、专题推断和最终答案仍遵循 `LLM_REASONING`。`LLM_MAX_OUTPUT_TOKENS` 是首轮上限，不是每次调用都必须消耗的目标；只有真实截断、超时或格式错误时，`plan_model_retry` 才按原因在 `LLM_ADAPTIVE_*` 硬上限内临时扩容、延时、切分或反馈重做。这样既保留长答案能力，也避免短 JSON 节点生成数千个无用思考 token。

长答案反思也可能用满8192额度；该情况会明确中止当前执行并保留已完成成果，不标为核验通过。目前只有分段阅读具备下述二分恢复，答案生成和反思尚无自动拆分策略。

整篇不超过 `READING_VERBATIM_MAX_CHARS`（默认1200）时原样保留，终端显示阅读模型调用0；设0关闭，该值参与阅读版本。长文片段由 `READING_CHUNK_CHARS` 控制，默认2200。阅读首轮关闭思考；截断可二分一次，子段再截断即停止。最多处理“原段＋两个子段”三个输入单元；每单元仍可能有界重试，不等于整段最多三次HTTP请求。两半都成功才保存完整成果，每子段先去重再最多六项。简单事实的证据检查也使用直接短输出，分析/预测与最终生成继续遵循全局思考开关。

应用层 `LLM_CONCURRENCY=2` 只有在 Ollama 服务也允许两个并行槽位时才会真正同时推理。本机 RTX 4080 / `gemma4:26b` 使用 `OLLAMA_NUM_PARALLEL=2`、`OLLAMA_FLASH_ATTENTION=1`、`OLLAMA_KV_CACHE_TYPE=q8_0`；重启 Ollama 后 runner 应显示 `-np 2`、`--flash-attn on`、`--cache-type-k q8_0 --cache-type-v q8_0`。这是本机实测档，不是所有显卡的默认建议；出现显存不足或总吞吐下降时先把并行降为 1。Windows 用户环境变量要在 Ollama 启动前生效，修改后必须完整退出并重启服务。

最终仍截断的任务会持久标为不自动重试，后续补搜批次也跳过。可修改配置后重新研究，或显式 `--retry-failed` 重置；数据库只增加任务标记列，不删除历史成果。

`--retry-failed` 不绕过模型/配方/工作流兼容性检查；配置变化造成不兼容时只能重新发起研究，不能靠该参数强行续跑。

## 5. 文件变化后的增量同步

```bat
agentic-rag-ingest
```

处理新增/修改/删除，跳过未变文件，不是每次全库重建。非空索引不会仅因重启问答自动同步。

按需选择一种监听方式：

- 独立进程：`agentic-rag-ingest --watch --interval 2`，先同步，再轮询，Ctrl+C 停止。
- 问答后台：在 `.env` 设 `KNOWLEDGE_WATCH_ENABLED=true`，重启 CLI；默认是关闭。

二者共用增量逻辑，但跨进程没有知识索引写锁，不建议同时启动多个写入者。`--rebuild` 会重置当前配置集合再重建，仅确实需要时使用。普通文档解释更新不需执行它。

## 6. 研究恢复和成果检查

将占位编号替换成终端显示的真实值：

```bat
agentic-rag --runs
agentic-rag --status RUN_ID
agentic-rag --status RUN_ID -v
agentic-rag --inspect-reading READING_ID
agentic-rag --resume RUN_ID
agentic-rag --resume RUN_ID --retry-failed
agentic-rag --repair-memory
```

`--runs`、`--status`、`--inspect-reading` 不调用对话模型；可能初始化/打开研究数据库。`--list-tools` 连研究数据库也不初始化。

`--resume` 对没有待推进节点/任务且已有答案的检查点通常直接离线展示，不更新新闻、不连接或卸载 Ollama、不启动索引监听，不改写运行状态或事件；即使当前模型不可用也能查看。例外是v21或当前工作流留下的半读END记录：有原文且模型/阅读配方兼容时，重新进入阅读，补齐缺失分段，不重搜。正常的新流程未读完会直接停在阅读检查点，不再走到END。已有草稿但仍有待执行任务的研究不能离线展示，`--retry-failed` 也不跳过正常执行检查。其他不兼容版本需重新提问。`--retry-failed` 重置失败/旧中断任务尝试预算，从保存材料重新进入筛选再阅读，完成任务仍复用。

“节点结果已写入、下一检查点尚未提交”的中断不能只凭 `snapshot.next` 为空判完成；程序同时检查 `snapshot.tasks`，保留已完成节点结果并让图继续推进。无任务且无答案会明确提示异常，不伪装成完成。中断/失败会记录 `run_failure` 类型和原因，终端显示最后阶段、工具/证据/阅读数量、已保存结果和恢复命令。`KeyboardInterrupt` 只证明捕获中断，不能判断是谁按了 Ctrl+C。

恢复后，旧失败不再作为当前“停止原因”显示；完整诊断中的 `last_failure` 和历史事件仍保留它。当前 `failure` 仅表示最近一次执行的失败/中断。结构错误会先提取真实字段原因，再做长度限制，避免长 JSON 挤掉纠错信息；终端保留受控模型错误的具体原因。

### 整场执行预算

CLI 每次执行建立跨节点、跨 Agent 的共同预算：`RESEARCH_TOTAL_TIMEOUT=1800` 秒、`RESEARCH_MAX_MODEL_CALLS=160` 次，均可设为0关闭。终端显示实际限额，事件保存本次配置。调用次数包括内部自适应重试和失败尝试；领取额度是线程安全的，不能靠并发绕过。恢复时累加已保存的执行秒数和调用数，不计关闭程序后的等待时间；旧记录缺失计量仍有缺口，不能推断完整历史成本。

超过预算会停止继续派发，保留已完成阅读和检查点，不把部分回答标成成功。需要继续时提高相应配置再恢复；不会暗改新闻日期或删掉资料。`RESEARCH_TIMEOUT` 仍是子任务批次的局部期限，但不能延长整场剩余额度。模型/新闻 HTTP 阶段超时会缩到剩余预算内；已经发到模型服务的推理不能由这个协作式期限强制取消，HTTP分阶段等待和第三方阻塞仍可能造成墙钟超出。因此这不是严格的1800秒进程杀死器；验收脚本另有独立进程看门狗。

`--repair-memory` 补写向量，不重新阅读，可能加载嵌入模型；失败时停止，不能因命令返回就假定全部修好，应看 `failed` 和 `remaining`。不要删数据库来解除运行锁。

新闻分页默认每页20条；明确只需N篇且N小于20时，每页请求N条，主题筛选批次也不超过尚缺数量。过滤掉无关或不符元数据的新闻后继续翻页，不把“请求两条”等同于“取得两篇有效证据”。这只减少不必要扫描，不修改关键词、日期、排序或最终数量。稀疏词取20条仍可能触及服务端查询时限；没有因此宣称已解决服务器全文检索能力。2026-10-02同一“新疆美盛”不限日期查询实测：2条0.13秒成功，20条8.12秒查询超时，记录在本机 `evaluation/runs/news-live-20261002-final/sparse-query-probe.json`；另有 `scripts/news_query_probe.py` 可重做对照。

本轮阅读配方与工作流版本已升级，旧研究保留历史结果；旧完成标记不代表通过新规则。直接 `--resume` 仅显示已结束结果，要按新规则重验请重新提交问题。兼容的影响评分和阅读结果仍会复用；改变配方不修改旧成果。

新闻 API 只对临时 HTTP 429/502/503/504 重试，包含首次最多三次，默认等待 0.5 秒、1 秒；等待不占网络槽位。如果 503 的已知 JSON 错误协议明确报告查询不可用/超出服务端查询时限，则不重复提交同一请求，也不擅自缩短日期。服务指定 0–5 秒的数字 `Retry-After` 时遵循它，超过 5 秒或日期格式提示则本次停止，不提前轰炸服务。认证失败、连接失败和请求超时不盲目重试。两种终端模式都会显示实际重试次数；持续失败时保留前页候选、记录来源错误和“分页未取完”，不能称为完整召回。仅识别并转述已知错误类型，不回显任意服务端正文。此策略只修复客户端容错，不能修复远端数据库/网关故障。

已部署的新闻服务另返回稳定错误码：`query_timeout` 不重试相同查询；`database_unavailable` / `busy` 可有限重试；`internal_error` 返回 HTTP 500，不再冒充查询超时。客户端保留兼容旧错误正文的分支。服务返回 `X-Request-ID`，分页、重试和失败事件会记录相同编号；`-v` 显示成功分页编号，错误说明直接带编号，可对照服务端 `request_error` 日志。客户端只接纳规定形状的编号和已知错误码，不回显任意错误正文。新闻 503 也不会在 CLI 被误报为 Ollama 503。

## 8. 数据、备份与故障定位

默认 `.chroma/` 保存索引、原文、问题、任务、检查点和分析；不要提交 Git。路径可由配置改写，不能假定都在默认目录。备份时停止相关进程，成套保存研究库与检查点及需要的索引；不要只复制活动 SQLite 主文件而忽略 WAL。

故障按层定位：解释器/安装 → Ollama 服务与模型 → 本机连接/代理 → 嵌入模型与知识索引 → 新闻认证/接口 → 工具事件 → 证据与反思。

```bat
python scripts\diagnose_ollama.py
python -m pytest -q
python scripts\docs_sync.py --check
```

诊断脚本会连接配置的 Ollama；测试和文档检查无需真实新闻或模型服务。503 有多种原因，不能仅增加重试就断定解决。已知限制见[状态页](status.md)。

### 启动时连接失败，不等于模型正在加载

先启动 Ollama 应用，或在单独终端运行 `ollama serve` 并保持该窗口开启，再在项目终端执行 `agentic-rag`。程序不会自动启动服务或下载模型。服务已运行时，不需要重复启动第二个 `serve`；如提示端口被占用，应先确认已有服务。

预热的错误处理与研究链内部的模型自适应重试分开：

| 现象 | 当前行为 | 需要检查 |
|---|---|---|
| 连接拒绝、连接超时 | 一次失败即停止，显示脱敏服务地址；不再重复十次或发送额外卸载请求 | Ollama 是否运行、地址和端口；远程服务还需检查网络/代理 |
| HTTP 429/502/503/504 | 显示实际状态码，在 `OLLAMA_WARMUP_ATTEMPTS`（包含首轮）内按 `OLLAMA_WARMUP_RETRY_SECONDS` 间隔重试 | 限流、服务日志与临时不可用，不能仅据此断言模型正在加载 |
| HTTP 404 | 停止，不自动下载 | 地址是否对应 Ollama API；在对应服务器运行 `ollama list`，核对 `LLM_MODEL` |
| HTTP 401/403 或其他 HTTP 错误 | 停止，不盲目重复加载 | 认证权限、模型兼容性和服务资源日志 |
| 读取/其他请求阶段超时 | 停止重复提交预热请求，提示服务端可能仍在加载 | 等待并检查内存/显存；必要时调整 `LLM_REQUEST_TIMEOUT` |

预热连接超时上限为 5 秒（配置请求超时更小时取更小值）；读取、写入和连接池等待采用 `LLM_REQUEST_TIMEOUT`，最低 1 秒。它们是 HTTP 各阶段超时，不是整场研究或严格的预热总耗时上限。客户端超时也不能取消已经开始的服务端加载。

程序自行创建的预热连接会关闭，不关闭调用方传入的连接。正常退出的卸载通知各 HTTP 阶段上限为 5 秒，通知失败不覆盖原错误；预热失败后不再额外卸载。失败且服务未报告的用量仍标为未知，不用零冒充实际模型消耗。
